# Contributing to OptimCE Production

Thank you for your interest in contributing! Issues and pull requests are
welcome from everyone. By participating in this project, you agree to abide by
our [Code of Conduct](CODE_OF_CONDUCT.md).

## Where to Contribute

The OptimCE platform is split across several repositories under the
[OptimCE organization](https://github.com/OptimCE):

- **This repository** is the reference **production deployment**. It is the
  right place for changes to the Docker Compose stack, the KrakenD builder
  configuration, the nginx templates, the Keycloak realm template, the database
  bootstrap SQL, the backup jobs, and the `docker-stack` wrappers.
- **Service code** (backend, frontend, microservices) lives in the individual
  service repositories. This deployment only runs **published images**
  (`ghcr.io/optimce/*`) — it builds nothing. If your change concerns how a
  service behaves, please open your issue or pull request in that service's
  repository.
- **Local development** belongs in
  [OptimCE/monorepo](https://github.com/OptimCE/monorepo), which aggregates the
  services as git submodules and provides the development Docker Compose
  environment.

## Setting Up a Deployment

```bash
git clone https://github.com/OptimCE/production.git
cd production
# Review docker-compose/.env and replace every placeholder value
./docker-stack.sh start
```

On Windows, use `docker-stack.bat` with the same commands.

You need Docker and Docker Compose. On Linux, `docker-stack.sh` checks that the
`docker` systemd unit is active and stops if it is not. The
[README](README.md) covers the profiles, the configuration files, and the backup
jobs.

## Reporting Bugs and Suggesting Features

Open a [GitHub issue](https://github.com/OptimCE/production/issues) (or one in
the relevant service repository). For bugs, include what you did, what you
expected, and what happened instead — the output of `docker compose logs` for
the failing service helps a lot.

For security vulnerabilities, **do not open a public issue**; follow the
[security policy](SECURITY.md) instead.

## Submitting Pull Requests

1. Fork the repository and create a feature branch from `main`.
2. Make your changes. Keep each pull request focused on a single topic.
3. Make sure the stack still starts (`./docker-stack.sh start`) and that the
   application answers on the configured `DOMAIN`.
4. Open a pull request against `main`, describing **what** you changed and
   **why**.

Notes:

- **Never commit real credentials.** The values in `docker-compose/.env` are
  placeholders meant to be replaced on each installation; keep them that way in
  the repository.
- Do not commit files generated by the `init` profile (the compiled
  `krakend.json`, the rendered `prod-config.json`, `default.conf`,
  `config.json`, the downloaded Keycloak provider jars). They are listed in
  `.gitignore` and are re-created on every start.
- When adding a new annex service, follow the three-step checklist at the end of
  the [README](README.md) so the gateway, the database, the backup job, and the
  network stay in sync.
- Small documentation fixes are welcome as direct pull requests; for larger
  changes, opening an issue first to discuss the approach can save you time.

## Commit Messages

Use short, imperative commit messages, preferably following the
[Conventional Commits](https://www.conventionalcommits.org/) style used in this
repository:

```
feat: add billing service to the production stack
fix: correct krakend upstream port for allocation-key-generation
chore: bump keycloak image to 26.5.5
docs: document the migration profile
```
